# 设计思路

## 从最终产物反推输入

以真实产品的 cfg、def、src 与工程成员为依据，划分三类信息：项目需要人工确认的需求进入 JSON；芯片复用、依赖与固定装配进入平台和模块资料；代码布局、注释和用户区进入模板。旧 Excel 和旧板级目录用于参考，不作为生成时复制的底稿。

```text
真实头文件/驱动/引脚资料 → 来源扫描 → 模块库与平台资料
                                      ↓
                              网页配置 ↔ 项目 JSON
                                      ↓
                           校验与模块参数映射
                                      ↓
                       代码模板 + 工程适配器 → 输出目录
```

## 各层职责

- `ui/source-settings.json` 指定去哪里读版本枚举、功能枚举和平台源码。扫描仅发现和核对能力，未知功能需维护者审核。
- `modules/*.json` 定义模块、实例字段、器件与依赖；`ui/frontend-fields.json` 对复杂表单进行补充。网页渲染与 JSON 迁移分别位于 app.js 和 frontend-model.js。
- `platforms/<mcu>.json` 提供引脚复用；`<mcu>-defaults.json` 提供已审核的固定生成默认值；`<mcu>-generation.json` 描述模块文件、编译成员和平台规则。
- `generator/modules/` 将用户语义转换为 C 对象、枚举、总线引用和模板上下文；实例数量由配置数组决定。
- `templates/` 决定代码风格和必要注释；`generator/projects/` 负责 IDE 工程装配；写入器负责用户区合并和生成区保护。

一个板子可同时描述 Boot/App，它们的功能选择可以不同；共享板级实例必须满足已实现的共享约束。器件引用公共总线，由公共初始化统一配置引脚，避免各模块重复定义同一资源。

## 扩展边界

新器件不是只增加下拉选项：还需审核接口、依赖、对象映射、模板和工程成员。新 MCU 要有独立引脚资料、默认值、模板和装配规则；新工具链要有工程适配器。扫描到源码、网页能填写、生成器能输出、真实工程能编译是不同验收阶段。

项目 JSON 是用户输入和复用入口；报告、浏览器快照和生成状态不作为项目需求来源。旧 JSON 的兼容迁移不得静默丢弃未知配置。特殊项目逻辑放在约定用户区，公共能力的长期修改应进入模板和生成器。
